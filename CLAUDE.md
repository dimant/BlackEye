# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BlackEye bridges an Icom D-STAR radio running in **Terminal Mode** (connected over USB/serial) to D-STAR **reflectors reached over IP**. Audio is never decoded — AMBE voice frames are passed through opaquely; the code only reframes packets between the serial terminal protocol and the network reflector protocol.

The protocols are reverse-engineered from packet captures, not from a published spec.

## Build / run

```bash
dotnet build                    # solution (net6.0; SDK warns NETSDK1138, harmless)
dotnet run --project BlackEye   # runs the currently-wired entry point
```

There are no tests and no test project. Verification is done by comparing generated bytes against the captures in `dumps/`.

The serial side uses `System.IO.Ports` with a hard-coded `"COM4"` port name (`Program.cs`), so the app only actually runs on Windows against a real radio. It builds and the protocol classes are exercisable on macOS/Linux.

## Protocol reference — read before touching byte layouts

Two documents are the source of truth for every offset and magic byte in the code:

- `BlackEye.Connectivity/Readme.md` — DPlus (REF/XRF), DCS (DCS/XLX/JPN), and the Icom terminal serial protocol, field by field.
- `dumps/significant_bytes.txt` — meaning of the frame sequence/flag bits and the five frame variants (empty voice, sync data, EOT, etc.).

`dumps/*.txt` are the raw Wireshark and serial captures those docs were derived from; use them to confirm any layout change.

## Architecture

Two projects: `BlackEye.Connectivity` (all protocol/transport code, no policy) and `BlackEye` (console host + the state machines that connect the two sides).

Each protocol side is built from the same four pieces:

| piece | terminal side | network side |
|---|---|---|
| transport (`IConnection`) | `SerialConnection` | `UdpConnection` |
| byte-stream → packets | `IcomTerminalReader` | `DPlusNetworkReader` |
| callback interface | `ITerminalListener` | `IDPlusListener` |
| packets → bytes | `IcomTerminalWriter` | `DPlusNetworkWriter` |

Wiring is always: transport's `ReceivedCallback` → reader → listener implementation → writer → transport's `Send`. Readers never write and writers hold no state; all sequencing lives in the listener implementations.

**Framing differs by transport.** Serial is a continuous byte stream, so `IcomTerminalReader` extends `BlockDataReceiver`, which feeds bytes into a TPL Dataflow `BufferBlock<byte>` consumed by a background loop; it resyncs on the `0xFF` packet terminator, then reads the length byte and that many bytes. UDP is already message-framed, so `DPlusNetworkReader.Receive` parses a whole datagram per call and validates `buffer[0] == buffer.Length`.

**Bridging (`BlackEye/DPlusHandler.cs`)** — the class implements *both* listener interfaces through two inner classes, `TerminalToDPlus` and `DPlusToTerminal`, sharing one `LockedState` (Disconnected/Idle/Receiving/Transmitting/Error) and one `ConcurrentQueue<byte[]>`. The direction asymmetry matters:

- Radio → network is push: each terminal frame is immediately written to UDP. Headers are resent 5× at the start and every 20 frames because UDP drops them.
- Network → radio is ack-pulled: incoming DPlus frames are *enqueued*, and one is dequeued and sent only when the radio acks the previous frame (`OnFrameAck`/`OnPong`). If the queue is empty the writer's canned empty-voice frames keep the radio's timing alive; after 100 empty frames the transmission is torn down.

The class doc-comment at the top of `DPlusHandler.cs` is the authoritative description of the intended state machine.

**`LockedState`** is the concurrency primitive throughout: `CompareExecute` / `CompareExchangeExecute` run an action only while holding the lock and only if the state still matches, using a double-checked read. State transitions must go through it — the reader thread, the ping timer thread, and the UDP receive callback all mutate state.

**`PingHandler`** implements every keepalive: a 1 s timer calls `pingAction`; any inbound traffic calls `Pong()` to restart it; 5 s without a pong fires `timeOutAction` and three consecutive timeouts fire `errorAction`.

## D-STAR conventions the code assumes everywhere

- Callsigns are fixed-width 8 chars, space padded; suffix is 4 chars. Strings are sliced straight out of the buffer with ranges — no trimming, no validation.
- A voice payload is always exactly 12 bytes: 9 AMBE + 3 data. `WriteFrame` throws if it isn't.
- End of transmission is signalled by the data bytes, not a packet type: `0x55 0x55 0x55` on the network side (`DPlusFramePacket.IsLast`), zeroed bytes 10–12 on the terminal side (`IcomTerminalFrame.IsLast`).
- **Rpt1/Rpt2 sit at swapped offsets in the two protocols.** The header writers take them in different parameter orders to compensate (`IcomTerminalWriter.WriteHeader(rpt2, rpt1, …)` vs `DPlusNetworkWriter.WriteHeader(rpt1, rpt2, …)`). Check the argument order against the reader properties whenever you touch header code.

## Current state

`Program.cs` wires `IcomTerminalEcho` — a serial loopback that records a transmission and plays it back to the radio, used to validate the terminal protocol. `DPlusHandler` is work in progress and is **not** reachable from `Main`; nothing constructs `UdpConnection` or `DPlusNetworkReader` yet. Callsigns (`AI6VW`), the COM port, and the reflector ports are hard-coded; there is no configuration layer.

Known gaps in the untested DPlus write path: `DPlusNetworkWriter.WriteHeader` copies the D-STAR header into itself instead of into the outgoing buffer, and `WriteLogin` builds a 27-byte buffer while its length byte and the spec say 28. The DCS protocol is documented in the Readme but not implemented.
